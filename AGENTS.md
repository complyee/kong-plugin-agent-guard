- The Kong companion (kong/agent-guard/, published as the LuaRock kong-plugin-agent-guard) packages the Lua snippets documented in src/lib/copy/plugins.ts (KONG_RECIPE) as one plugin with three modes: decide (online decideAction, default), verify (offline acr-grant-v3 Ed25519 check) and verify_jwt (claim binding after a JWT plugin) — why: the packaged code and the hand-built recipe must say the same thing until the recipe points at the package.
- This folder is the source for github.com/complyee/kong-plugin-agent-guard; push every change there, and keep spec/run.lua green on plain LuaJIT (mocked kong/ngx/resty APIs) — why: published code must not drift, and the sandbox has no Kong runtime.
- The verify mode rebuilds the acr-grant-v3 signed message in the exact field order of GRANT_MESSAGE_FORMAT in src/lib/grant-keys.server.ts (version, workspace, keyId, decisionId, agent, action, payloadHash, expiresAt, parent, root, depth, "|"-joined) — why: a grant must verify identically at every enforcement point.
- Kong outcome reports are single best-effort proxy observations in decide mode only, with HTTP detail codes and decision-correlated loss logs; response bodies are never logged — why: gateway telemetry must not imply durable delivery or business completion.
- Live checks live in spec/integration/ (Docker Compose: real Kong, dependency-free Node stand-in for ACR and upstream, Node runner); the stand-in must sign grants with the same acr-grant-v3 field order — why: it proves the plugin inside real Kong, which mocked unit tests cannot.
